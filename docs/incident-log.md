# Incident log

What has gone wrong, how it was noticed, what fixed it, and which rule or test
it left behind. Newest first.

Everything below the first section is Cambridge Calendar's history, inherited
with the engine. Every number is as measured on the date given and describes
Cambridge's data then, not yours now. Rules are referenced by their id in
[rules-and-edge-cases.md](rules-and-edge-cases.md), which also names each test.

## How to log a new incident

Log anything that reached readers, any blocked run you had to diagnose, any
source that was silently wrong or empty for more than a day, and any near miss
an audit found.

1. **Add a row at the top of the table** for your calendar's own history (start
   a "Your calendar" table above Cambridge's): the date; what happened, with the
   numbers (how many events, which source, wrong by how much); how it was
   caught (a reader, the gate, `cal doctor`, drift, the audit); the fix; the rule
   and test it produced.
2. **Leave the evidence**: the page that broke the scraper as a fixture, the run
   record, the quarantine if there was one. Copy a shipped bad run into
   `tests/fixtures/incidents/` if a test should replay it.
3. **Add a test that fails on the old code**, then the fix.
4. **Update [rules-and-edge-cases.md](rules-and-edge-cases.md)**: a new rule or
   edge case with its incident and test, or the new incident added to an
   existing rule's "Why". If you could not write a test, add it to the
   Untested list instead.
5. If it surprised you, add a line to the known traps in
   [operations.md](operations.md#known-traps).
6. Write the commit message the same way: what was wrong, with numbers, what
   changed, what you spot-checked against the live page.

Who noticed matters. "A reader emailed" means every check failed; the follow-up
is the check that would have caught it.
